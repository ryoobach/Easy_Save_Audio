# 2026-11-22 작업 회고 및 재작업 방지 메모

대상 저장소: `ryoobach/Easy_Save_Audio`  
대상 앱: **Easy Save Audio & Video**  
작성 목적: 오늘 수행한 테스트와 확인되지 않은 가설을 기록하여 다음 작업에서 같은 실험을 반복하지 않도록 한다.

> 주의: 이 문서는 오늘 확인된 사실과 미확정 가설을 구분한다. 로그의 기술적 검증 성공을 실제 플레이어 재생 성공으로 간주하지 않는다.

## 1. 오늘 작업 기준 버전 및 범위

- 오늘 오전 작업 기준 버전은 **v2.3.6**이었다.
- 이후 테스트/수정 작업은 **v2.3.8**을 기준으로 진행했다.
- 이 저장소는 유튜브 오디오/동영상 다운로드 및 변환 앱이다. 다른 프로젝트인 **My Latest Artifacts**와 혼동하지 않는다.
- 오늘 마지막 테스트 후 사용자가 피로를 호소하여 추가 빌드 없이 작업을 중단했다. 다음 작업은 사용자가 다시 시작하겠다고 할 때 진행한다.

## 2. 오늘 수행한 오디오 테스트와 결과

### A/F/G/H 프로필 비교

- A, F, G, H 프로필의 결과물을 사용자가 직접 들어 비교했다.
- 사용자의 청취 결과: 네 프로필 사이에 **뚜렷한 차이가 없음**.
- H 프로필은 `320 kb/s CBR`, `44.1 kHz stereo`, Loudnorm 비활성 조건이었다.
- G 프로필은 `320 kb/s CBR`, `48 kHz`, Loudnorm 활성 조건으로 비교되었다.
- H 결과 파일의 프레임/디코딩 검사는 통과했고, 로그상 프레임 누락이나 손상은 보고되지 않았다.
- A의 VBR Q2를 기본값 후보로 언급했지만, 오늘 확인된 내용만으로 기본값 변경을 확정하거나 구현한 것은 아니다.

**재작업 방지:** A/F/G/H의 단순 음질 비교를 같은 조건으로 다시 반복하지 않는다. 새 테스트는 기존과 다른 가설을 검증할 때만 수행한다.

### N 및 O로 지칭된 테스트

- 사용자가 보고한 재생 결과는 두 파일 사이에서 일관됐다.
  - **순정🎖️**: 재생 실패
  - **무명배우**: 재생 성공
- 이 결과는 N 및 O라고 부른 테스트에서 관찰됐다.
- 로그의 MP3 기술 정보와 디코딩/프레임 검사는 정상으로 나타났으나, 이는 Winamp 등 실제 플레이어에서의 재생 성공을 보장하지 않는다.
- O라고 부른 테스트 로그의 실제 `compatibility_profile` 값은 **`2.3.8_Q_MONO_192K`**였다. 사용자가 부른 O와 내부 프로필 식별자가 일치하지 않을 가능성이 있으므로 실행 파일의 프로필 버튼-설정 매핑을 확인해야 한다.
- Q 프로필은 `192 kb/s mono`로 확인됐으며, O 프로필 정의는 `128 kb/s stereo`로 기록되어 있다. 이 불일치는 우선 확인할 항목이지, 재생 실패의 원인으로 확정된 것은 아니다.
- 순정🎖️의 ID3 제목에서 🎖️ 문자가 `???`처럼 출력된 정황이 있어 메타데이터 문자 인코딩/플레이어 호환성을 가설로 남긴다. 원인 확정은 하지 않았다.

**재작업 방지:** 동일한 두 곡을 같은 설정으로 다시 인코딩하는 것만으로는 새 정보가 생기지 않는다. 먼저 O 버튼과 내부 프로필 ID의 매핑을 확인하고, 메타데이터 가설은 제목 태그만 달리한 통제 테스트로 분리한다.

## 3. 이전 검증 로직 문제의 교훈

- 과거 v2.2.0/v2.2.1에서는 실제 MP3가 `44.1 kHz stereo`이고 FFmpeg 디코딩이 성공했는데도 앱의 파서가 코덱/샘플레이트/채널을 `unknown` 또는 0으로 표시해 검증에 실패한 사례가 있었다.
- 당시 문제는 인코딩 실패로 단정할 수 없었고, 입력 MP3 정보와 디코딩된 PCM 정보를 혼동하거나 파싱하는 진단 로직의 문제 가능성이 컸다.
- v2.2.1에서 검증 실패만으로 결과 MP3를 삭제하지 않도록 한 변경이 기록되어 있다.
- 이후 진단에서도 **파일 생성/프레임 구조/전체 디코딩/실제 플레이어 재생**은 서로 다른 검사 단계로 취급한다.

**재작업 방지:** 진단 파서의 `unknown`만으로 변환 실패를 선언하거나 결과 파일을 삭제하지 않는다. FFprobe 등 구조화된 메타데이터 확인과 FFmpeg 전체 디코딩, 실제 플레이어 청취를 각각 독립적으로 판정한다.

## 4. 오늘의 미확정 가설 및 확인 필요 사항

1. **프로필 매핑:** 화면의 O 선택이 로그에서 Q로 기록된 이유를 확인한다.
2. **ID3 이모지:** 🎖️ 문자가 제목 태그에 포함될 때 일부 플레이어에서 문제가 생기는지, 제목 태그를 생략하거나 ASCII 제목으로 바꾼 대조군으로 확인한다.
3. **파일별 차이:** 같은 프로필에서 순정🎖️만 실패하고 무명배우는 성공하는 이유를 파일명/ID3 태그/오디오 프레임 데이터로 나눠 조사한다.
4. **실제 재생:** FFmpeg 디코딩 성공만으로 Winamp 재생 성공을 주장하지 않는다.

위 항목들은 아직 원인 확정 또는 해결 완료로 기록하지 않는다.

## 5. 내일 새 접근: 동영상 코덱 지원 범위 재정의

사용자가 제시한 방향:

- 동영상 코덱을 100여 가지씩 무작정 지원 대상으로 늘리지 않는다.
- 실제 대중화되어 널리 사용되는 컨테이너와 코덱 조합만 우선 대상으로 좁힌다.
- 지원 목록은 실제 사용 빈도와 호환성을 기준으로 선정한다.
- FFmpeg가 여러 형식을 처리할 수 있다는 사실과 앱이 공식적으로 지원/보장하는 형식의 범위를 혼동하지 않는다.
- 비주류 형식은 우선 지원 목록에서 제외하고, 지원하지 않는 경우 명확하게 안내한다.

**중요:** 구체적인 컨테이너/코덱 목록은 아직 확정하지 않았다. 내일 실제 사용성이 높은 조합을 검토한 뒤 확정한다. 확인 없이 백여 가지 목록을 만들거나 지원한다고 표기하지 않는다.

## 6. 다음 작업 시작 순서

1. 현재 main 브랜치와 앱 버전, 최근 변경 파일을 먼저 확인한다.
2. 오늘 기록한 프로필 매핑 불일치(O 선택 ↔ Q 로그)를 확인한다.
3. 이미 수행한 A/F/G/H의 동일 청취 비교는 반복하지 않는다.
4. 순정🎖️ 재생 문제는 ID3/파일 메타데이터와 오디오 프레임을 분리한 통제 테스트로 접근한다.
5. 동영상 지원은 대중적인 컨테이너·코덱 조합을 먼저 선정하고, 지원 범위를 작게 명확히 정의한다.
6. 원인 확인 전에는 무관한 인코딩 옵션을 한꺼번에 변경하거나 여러 변수를 동시에 바꾸지 않는다.
7. 새 빌드는 각 테스트가 검증할 가설과 성공/실패 판정 기준을 먼저 정한 뒤 진행한다.
